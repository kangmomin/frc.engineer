## 1. 사전 검토와 결정

오케스트레이터는 순위의 모집단과 기록 출처, 샘플 결합의 시간 정합성, 계정·연결 상태의 소유권을 먼저 확인했다. 작업을 랭킹 API·화면, 선택 랩 API·분석 화면, 웹 코드 분할, Sender 처리 생략으로 나눴다. [Assumption] 난이도는 랭킹과 분석의 FE·BE 각각 상, 웹 분할과 Sender 수정 각각 중으로 판단했다.

랭킹의 BE·FE 독립 리뷰에서는 커서 cutoff의 한계, 시각 정밀도, HTTP 오류, Overview의 PB 상태 분리, 동점·null·주변 조회, 계정 전환 보호를 반영했다. 구현 후 지적된 커서 UUID 정규화와 로컬 기록의 잘못된 검증 문구도 수정했다.

랩 분석의 독립 사전 리뷰 후 API와 화면 계약을 확정했다. 구현 후 양측 리뷰에서 발견한 모호한 Δt 구간 연결, 조각이 많은 trace의 이차 시간 복잡도, 중복 거리의 X/Z 쌍 손상, 결측 거리를 되감기로 판정하는 문제, 랩마다 복제되던 전체 기록 인덱스를 수정했고 재리뷰 승인을 받았다.

P02·P04도 독립적인 소스·계획 검토를 거쳤다. 추가 상세 리뷰를 맡은 두 에이전트는 사용 한도 오류로 실행되지 않았다. [Assumption] 이미 검토된 최소 범위를 오케스트레이터가 FE·BE 순서로 직접 구현하고 검증했다. 추가 독립 사후 리뷰를 받았다고 간주하지 않는다. 외부 CLI 리뷰어는 사용하지 않았다.

## 2. 구현 내용

### 랭킹

- 전체 세션의 유효 최고 랩(PB)과 실제 Time Trial 기록을 구분한다. 기존 `session_type`의 정규화된 `Time Trial`만 TT에 포함한다. 레거시 `/leaderboards/tt` 배열은 기존 PB 계약을 유지한다.
- 전체 모집단에서 순위를 계산한 뒤 페이지를 자른다. 200위 이후, 이전·다음 페이지, 로그인 사용자 및 선택한 드라이버 주변 조회를 제공한다. 프로필 PB와 같은 기준을 사용한다.
- 기존 일관성 산식을 유지하면서 모집단 표준편차(초)와 평균 랩의 ±1초 이내 비율을 설명과 함께 표시한다. 최소 5개 유효·plausible 랩이 필요하다. 피트·SC 제외는 아직 구현 범위가 아니다.
- 계정의 업로드 이력, 기록의 기본 형식·범위 검사, 로컬 저장 기록을 구별해 표시한다. 이를 치트 방지 검증으로 표현하지 않는다.

`GET /leaderboards/records`는 `board=pb|tt|pace`, `track`, `format`, `limit`, `cursor` 또는 `around`를 받는다. 행·전체 참가자 수·선두 기록·로그인 사용자의 순위·10위와의 차이·양방향 커서를 한 SQL statement에서 계산한다.

[Assumption] 기본 보드는 PB, 페이지 크기는 50이다. 동점은 결정적 기준을 사용하는 순번이며 공동순위가 아니다. 커서는 조회 조건에 묶이고 시각의 마이크로초 정밀도를 보존한다. `asOf`는 이후 timestamp의 업로드를 제외하는 cutoff다. 늦게 커밋된 기존 업로드, 삭제, 밴까지 고정하는 보존 스냅샷은 아니다.

Overview의 PB 조회는 Rankings의 보드·페이지와 독립적이다. 11위가 10위와 동점이어도 톱10으로 표시하지 않으며, 10명 미만일 때의 차이 null을 0으로 바꾸지 않는다. 주변 조회 대상과 로그인 viewer를 구별하고, 계정·View As·조회 조건 변경 후 이전 응답이 새 화면을 덮지 않도록 한다.

### 랩 분석

선택한 완료 랩의 원래 샘플 주기를 보존하는 trace API, 거리별 Δt, 공통 커서, 실제 X/Z 지도, 구간 확대, 분석 채널 선택을 구현했다. 같은 거리의 실제 랩 시계를 비교하고 공식 완료값은 별도로 표시한다. 없는 신호를 0으로 바꾸거나 데이터 공백을 연결하지 않는다. flashback과 결측 좌표는 공통 시도 경계에서 다룬다.

90초 합성 기록에서 timing 1,800행, controls·motion 각각 5,400행, status 180행을 반환했고, 20 Hz timing 사이의 16.67 ms 제동 펄스가 보존됐다. 전체 응답은 2,011,966 B, 250–330 m 구간은 31,725 B였다. 범위 조회도 입력 파일을 스캔하므로 같은 비율의 CPU 절감으로 해석하지 않는다.

A03·B01은 관측에 근거한 코너 단계 분석과 최대 3개의 실험·재측정 제안을 제공한다. 수동 라벨과의 비교 및 실제 재주행 효과는 검증하지 않았다. A13은 단순 강한 제동을 휠 잠김으로 표현하던 문구와 근거 없는 브레이크 처방을 교정했다. 실제 휠 잠김 검출은 남아 있다.

### 웹·Sender 처리 비용

Hub와 라이브 화면, Hub의 개별 화면, 라이브의 선택 뷰와 셋업 화면을 필요할 때 불러온다. 계정·View As 상태는 Hub에, WebRTC와 인터컴 상태는 기존 부모에 유지한다. 청크 로딩 실패 시 돌아가기와 명시적인 새로고침을 제공한다.

| 로컬 측정 | 변경 전 | 변경 후 |
|---|---:|---:|
| Hub 첫 진입 JavaScript 원본 | 904,567 B | 203,755 B |
| Hub 첫 진입 JavaScript gzip | 218,213 B | 67,681 B |
| Hub 준비 시간 중앙값, 3회 | 771.9 ms | 458.6 ms |
| Sender 합성 패킷 처리 중앙값, 3회 | 4.049 µs/op | 2.320 µs/op |
| 같은 Sender 패킷의 할당 | 12 allocs/op | 5 allocs/op |

Hub 측정은 Chrome의 60 ms 지연·500,000 B/s 제한과 gzip을 사용했다. 첫 진입 gzip은 약 69% 줄었다. Rankings의 첫 진입은 94 ms, 같은 세션의 재진입은 8 ms였으며 청크를 재사용했다. 인터넷·실제 사용자 기기의 성능 보장은 아니다. 비교 기준은 앞선 기능 구현 후의 904,567 B이며, 최초 연구 때의 902,360 B와 구별한다.

Sender는 현재 저장소의 클라이언트가 소비하지 않는 bare Dashboard의 생성·인코딩·전송만 명시적으로 끈다. 일반 Processor 생성자의 기본값과 0 Hz의 무제한 의미는 유지한다. Pitwall, 빠른 위치, 이벤트, PB 기록은 별도 경로로 계속 처리한다. 벤치마크는 4 Hz Pitwall tick 사이의 합성 패킷 처리이며 전체 앱 CPU나 실제 네트워크 대역폭 측정이 아니다. 외부 레거시 peer 호환성과 동적 capability 협상은 검증·구현하지 않아 P04를 완전 완료로 표시하지 않았다.

## 3. 최종 컨벤션 검토

- **Presentation:** HTTP 핸들러는 입력·인증·응답을, 화면은 조회 상태·커서·단위를 담당한다. 실제 기록과 추정·결측 상태를 구별한다.
- **Service:** 순위 계산은 Store 조회에, 샘플 파싱·시도 경계·결합은 analysis에 모았다. Sender에서는 Dashboard guard만 좁게 바꿨다.
- **Repository:** 한 SQL statement의 랭킹 조회와 공유 기록 인덱스를 사용한다. 저장 형식, DB 마이그레이션, 라이브 DTO를 추가하지 않았다.
- **Simplicity / Style:** 기존 스타일을 유지하고 새 의존성을 추가하지 않았다. 현재 선택 랩 쌍만 화면에서 보관하며, 전체 랩의 고밀도 trace 캐시를 만들지 않았다. 구현 범위와 검증 한계의 가정은 `[Assumption]`으로 명시했다.

## 4. 검증과 정리

- 전체 Go 테스트, 빌드, `go vet` 통과. 플랫폼 연동 테스트에는 별도 로컬 PostgreSQL 17 DB를 사용했다. 별도 DB가 필요한 파괴적 업그레이드 테스트는 실행하지 않았다.
- analysis·analysishttp 및 telemetry·rtc·sender race 검사 통과. Windows amd64 Sender 교차 컴파일 통과. Windows 실행·인스톨러 검증은 수행하지 않았다.
- 웹 60개 파일·639개 테스트, 전체 ESLint, TypeScript 및 remote·local 빌드 통과. Setup Manager의 분석 테스트 19개, 기존 Electron 테스트 20개, 타입 검사·renderer 빌드 통과. 새 분석 테스트를 웹 CI에 연결했고 같은 명령과 YAML 구문을 로컬에서 검증했다. 호스팅된 CI 실행 결과는 아니다.
- 실제 HTTP는 랭킹 13개·분석 8개 묶음 통과. Chrome은 랭킹 9개·분석 11개·프로덕션 코드 분할 7개 묶음과 기존 RTC·리플레이·인터컴·퀄리파잉 시나리오를 통과했다.
- View As 진입 중 개발 빌드와 프로덕션 빌드에서 각각 한 차례 일시적인 요청 취소가 관측됐다. 소스 수정 없이 후속 개발 빌드 검증과 프로덕션 검증 7회는 연속으로 통과했다. 마지막 검증에는 예상하지 않은 네트워크 실패나 런타임 예외가 없었으나, 앞선 취소의 원인은 확정하지 못했다.
- 24대와 2,000점 트랙맵을 사용하는 기존 WebRTC 크기 회귀 테스트가 통과했다. 라이브 DTO 확장은 없으며 기존 128 KiB backpressure와 256 KiB 메시지 제한을 유지한다. 새 고밀도 trace는 HTTP로 전송한다.

검증 근거는 위 JSON 파일과 API 계약에 보존했다. 이전 Dockerfile Go 버전 수정과 연구 문서는 유지한다. 이 작업의 임시 서버·DB·브라우저를 종료하고 테스트 토큰·합성 기록·임시 빌드 산출물을 정리했다. 이 문서는 구현 시점의 검증 기록이며, 이후 main 병합과 배포 상태는 Git 이력에서 확인한다.
