# 리플레이 전송 대기를 실시간 처리와 저장 잠금에서 분리

- **날짜**: 2026-09-05
- **이슈**: 리플레이 송신이 같은 DataChannel의 실시간 방송을 막고, `WalkReplay`의 네트워크 콜백이 전체 FileStorage 읽기 잠금을 점유해 다른 레이스 저장과 종료 체크포인트까지 지연시켰다.
- **결정**: DataChannel의 크기 확인과 송신만 직렬화한다. 즉시 송신은 잠금을 기다리지 않고 드롭하며, 대기 가능한 송신은 잠금을 풀고 정해진 시간 안에서 다시 시도한다. 리플레이는 저장 잠금 안에서 일관된 읽기 스냅샷을 준비한 뒤 잠금을 풀고 전송한다.
- **결정자**: 사용자(추가 리뷰 후 진행 승인) / 에이전트(구현과 독립 리뷰)
- **근거**:
  - 열린 실제 Pion 채널에서 잠금 경쟁 시 live 방송과 buffered 송신 deadline이 모두 멈추는 것을 재현했다. 큐 검사와 전송을 같은 잠금 안에 유지해야 128/256 KiB 예산을 동시 송신으로 넘지 않는다.
  - Unix에서는 rename으로 교체된 파일의 기존 핸들을 계속 읽는다. Windows는 원본을 OS 임시 파일로 복사하고 원본 핸들을 닫은 뒤 복사본을 읽는다. 복사·전송은 파일 전체를 메모리에 올리지 않는다.
  - Windows용 테스트를 Wine에서 실행한 결과, `FILE_SHARE_DELETE`를 추가하는 것만으로는 열린 목적지에 대한 기존 `os.Rename` 교체가 성공하지 않았다. 임시 스냅샷 방식은 같은 ID 교체·다른 ID 저장·삭제 중에도 기존 리플레이를 보존했다.
- **기각된 대안**:
  - 네트워크 콜백 동안 저장 잠금 유지: 느린 클라이언트가 캡처·종료를 지연시킨다.
  - Windows 저장을 삭제 후 rename으로 변경: 기존 저장의 실패·복구 의미를 바꾸고 원본이 사라지는 구간을 만든다.
  - 리플레이 전체를 메모리에 복사: 큰 레이스 파일마다 메모리 사용량이 증가한다.
- **트레이드오프**: Windows는 전송마다 파일 크기만큼 임시 디스크와 로컬 복사 시간이 필요하다. 복사 중에는 저장 잠금이 유지되지만 네트워크 대기 중에는 유지되지 않는다. 정상·오류 반환 시 임시 파일을 제거하며, 프로세스 강제 종료 시 OS 임시 폴더에 남을 수 있다. Wine 검증은 실제 Windows 장비 검증을 대신하지 않는다.
- **수정 내역**: `internal/rtc/peer_manager.go`, `internal/races/storage.go`, 플랫폼별 `replay_file_*.go` 및 송신·스냅샷 회귀 테스트.
- **재발 시 대응**: 두 잠금은 별도 병목이므로 하나만 수정해서는 해결되지 않는다. Save의 교체 계약과 스트리밍 메모리 상한을 유지한다.
